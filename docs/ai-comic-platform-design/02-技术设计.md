# AI 漫剧网页平台 V1 — 技术选型与数据模型

> 配套文档：`01-产品方案.md`（产品流程与十步定义）。本文只谈怎么实现。
>
> **代码从 0 开发**，不复用工作区其他项目的实现。唯一的外部输入是本机 5 个动态漫
> skill 沉淀的领域规范 —— 这些是制作约束，不是代码依赖。

## 一、领域规范来源

本机 5 个动态漫 skill 里的规范不是建议，是已经在实际制作中验证过的约束。V1 把它们从
"提示词里的文字要求"下沉为**数据库字段 + 校验规则**，让平台能自动挡住违规内容，而不是
靠 AI 每次自觉。

| Skill | 取什么 | 落到哪里 |
|-------|--------|----------|
| `dongtai-man-character` | 一致性锚点（不可变特征/禁用变化/定妆关键词串）、声音特质、标志性动作 | `asset` 表字段，第五步锁定的核心 |
| `dongtai-man-rhythm` | 节奏时间轴（铺/抑/爆/转）、爽点分型、强动态预算 ≤3、平淡期 ≤60s | `episode`/`beat` 表 + 第三步门禁 |
| `dongtai-man-writing` | 场景头格式、动态三级（微/中/强）、嘴部幅度分级（微/中/大）、单句 ≤10 字 | `scene_take`/`shot`/`shot_dialogue` 字段 + 校验 |
| `dongtaiman` | 标准分镜块字段、转场枚举、字幕时长规范 | `shot` 表结构直接对齐 |
| `seedance-manual` | `@素材` 引用契约、镜头语言枚举、时间轴式提示词、禁写实真人脸 | `shot_reference_binding` 表 + 提示词编译器 |

第七章逐条说明这些约束怎么编码成字段和校验。

### 1.1 两个从产品流程直接推出的设计决定

**一、参考图用外键绑定，不用名字匹配。** 如果分镜表存 `scene_name` 字符串、生成时再去
素材表按名字查，那么名字对不上时只有两种结果：报错，或者静默不挂参考图。静默失败是更
坏的一种 —— 图生成出来了、任务成功了、只是角色长得不对，要到人眼看片才发现。V1 用
`asset_id` 外键，名字只做显示，绑定关系由数据库约束保证。

**二、素材从确认后的剧本提取，不从原文。** 方案第四步已经论证过：剧本改编可能合并角
色、删减场次。从原文提取会得到剧本里不存在的素材。同时保留 `source_ref` 回溯到原文段
落，方便核对。

## 二、技术选型

### 2.1 总体

| 层 | 选型 | 理由 |
|----|------|------|
| 后端 | Python 3.11 + FastAPI | 异步 IO 适合大量 provider 调用；工作区已有 Python 环境 |
| 数据模型 | Pydantic v2 | 与 FastAPI 天然集成，schema 校验和 JSON 序列化一套搞定 |
| 持久化 | SQLite + 文件系统 | 见 2.2 |
| ORM | SQLAlchemy 2.0 Core | 只用 Core 不用 ORM 关系映射，避免 lazy load 惊喜 |
| 迁移 | Alembic | schema 会随迭代改，手写 ALTER 容易漏 |
| 前端 | Vite + React 19 + TypeScript | 见 2.3 |
| 前端状态 | TanStack Query | 任务轮询、缓存失效、乐观更新都是现成的 |
| UI | Tailwind + shadcn/ui | 逐镜卡片墙 + 侧边导航，不需要自己写设计系统 |
| 任务执行 | 线程池 + 落盘 Job | 单机自用，不引 Redis/Celery |
| 视频合成 | FFmpeg CLI | 子进程调用，不用 Python 绑定（版本兼容问题少） |
| 质检 | ffprobe | 同上，读流信息 |
| 测试 | pytest + Playwright 同步 API | 与本机既有约定一致 |

端口：后端 `127.0.0.1:8012`，前端 `127.0.0.1:3000`（对齐方案里的 localhost:3000）。
一个 `start.ps1` 同时拉起两个进程。

### 2.2 为什么用 SQLite 而不是单文件 JSON

单文件 JSON（一个 `project.json` 存整个项目）在本平台会出问题：

- 一部剧 10 集 × 每集 60 镜 = 600 个 shot，每个 shot 还要挂多版本关键帧/视频/配音，
  单文件会膨胀到几十 MB，每次改一个字段都要全量重写。
- 方案要求"每个素材保留生成版本"。版本表在 JSON 里就是数组套数组，查"当前生效版本"
  要遍历；SQL 里是一条 `WHERE is_current = 1`。
- 批量操作要按条件筛选（"本场次所有未确认关键帧"）。JSON 只能全量加载后在内存过滤。

分工：**结构化数据进 SQLite，二进制媒体留文件系统**。数据库只存相对路径。
SQLite 开 WAL 模式，单机单进程够用。

同时保留 `export/project.json` 导出接口 —— 便于人工检查和跨机迁移，但它是**导出产物，
不是真相来源**。

### 2.3 前端为什么用 React 而不是服务端渲染模板

服务端渲染模板（FastAPI + Jinja2 + 原生 JS）能省掉 Node 工具链，但本平台的界面复杂度高一档：

- 逐镜卡片要同时显示视频预览、配音播放器、字幕、两套重生成按钮
- 版本切换要即时预览，不能每次都整页刷新
- 批量任务进行中要实时更新几十张卡片的状态
- 十步导航要根据 stale 状态动态标记

这些用原生 JS 手写 DOM diff 会很快失控。React + TanStack Query 的轮询失效机制正好
对应"任务完成后刷新受影响的卡片"。

本地自用不需要 SSR，Vite 开发服务器 + `/api` 代理到 8012 即可。

### 2.4 外部服务抽象

六类 provider，统一接口 + 各自适配器：

```
provider/
  base.py          # Provider 抽象：submit() / poll() / fetch_result()
  text/            # LLM（OpenAI 兼容）
  image/           # 文生图 + 图生图（参考图注入）
  video/           # 图生视频（Grok，见 §2.5）
  tts/             # 配音（Edge TTS 免费兜底 + 商业 TTS）
  voice_clone/     # 声音克隆
```

统一契约：所有 provider 实现异步提交 + 轮询，`provider_task_id` 落盘后才进入等待状态。
顺序不能反 —— 先提交后落盘的话，进程在这两步之间挂掉就丢了 task_id，付费任务只能重新提交。

`MOCK_MODE=true` 时全部返回占位产物（纯色图/静音音频/静态帧视频），不依赖外部 API
即可跑通完整链路。这是开发和测试的默认模式。

### 2.5 视频 provider：Grok（apib.ai 网关）

**提交**

```
POST https://api.apib.ai/v1/videos/generations
Authorization: Bearer <token>
Content-Type: application/json

{
  "model": "grok-imagine-1.5-video-apimart",   // 别名 grok-imagine-1.5-video-ext
  "prompt": "<shot.video_prompt 编译产物>",
  "image_urls": ["<公网 URL>", ...],            // 最多 7 张
  "size": "16:9",
  "duration": 10,                               // 整数秒，6–30
  "quality": "720p"
}
```

**轮询**

```
GET https://api.apib.ai/v1/tasks/{task_id}?language=zh
Authorization: Bearer <token>
```

**返回字段 → 表字段映射**

| 返回字段 | 落到哪里 | 说明 |
|---------|---------|------|
| `data.id` | `job.provider_task_id` | 提交后立即落盘，再进 `waiting_provider` |
| `data.status` | `job.status` | `completed` → 拉取产物；失败态 → `job.error` |
| `data.progress` | `job.progress_current` | 0–100，驱动进度条 |
| `data.result.images[].url` | 下载后写 `clip_version.file_path` | **不能只存 URL** |
| `data.result.images[].expires_at` | `clip_version.remote_expires_at` | unix 时间戳 |
| `data.cost` / `data.credits_cost` | `generation_log.cost_estimate` | 逐次记账 |
| `data.actual_time` | `generation_log.latency_ms` | 实测耗时，用于估算后续批量 |

**四条硬约束（已编进 schema）**

1. `duration` 必须序列化成**整数**，不能是 `"10"` 或 `10.0`。所以
   `shot.planned_duration_sec` 用 `INTEGER`，不用 `REAL`。
2. `duration` 范围 **6–30 秒**，已写进 `CHECK` 约束。
3. `image_urls` 最多 **7 张**且必须是**公网 URL** —— 本地路径要先上传图床，
   `keyframe_version.remote_url` / `remote_expires_at` 就是为此存在。
4. 产物 URL 带 `expires_at`，轮询到 `completed` 必须**在同一个 job 内下载落盘**，
   不能只存 URL 等用户点播放时再取。

## 四、数据模型

### 4.1 通用约定

所有可生成实体共享四组字段，这是整个设计的骨架：

| 字段组 | 字段 | 作用 |
|--------|------|------|
| 身份 | `id` (TEXT PK, uuid) | 主键用 uuid，不用自增 —— 版本表跨表引用需要稳定 ID |
| 状态 | `status` | `not_generated` / `generating` / `pending_review` / `confirmed` / `locked` / `failed` |
| 签名 | `own_signature`、`upstream_signature` | 失效推导的唯一依据，见 4.9 |
| 时间 | `created_at`、`updated_at` | ISO 字符串，SQLite 无原生时间类型 |

版本化实体拆成两张表：主表存"当前状态 + 指向当前版本的指针"，版本表存每次生成的结果。

反面做法是把 `image_path` / `image_url` / `image_signature` / `image_error` 这类字段
平铺在主表上。那样每加一种媒体就要加四个字段，主表迅速膨胀到几十列，而且**天然只能
存一个版本** —— 重新生成必然覆盖原结果，这与方案第六章第 2 节"保留多版本、可切换"
直接冲突。

### 4.2 项目与步骤状态

```sql
CREATE TABLE project (
    id                TEXT PRIMARY KEY,
    name              TEXT NOT NULL,
    source_text       TEXT NOT NULL,          -- 小说正文
    source_signature  TEXT NOT NULL,          -- sha256(source_text)，全链失效的根
    -- 项目设定（第一步填写）
    style_preset      TEXT NOT NULL DEFAULT '',   -- 画面风格描述
    aspect_ratio      TEXT NOT NULL DEFAULT '16:9',
    resolution        TEXT NOT NULL DEFAULT '1920x1080',
    fps               INTEGER NOT NULL DEFAULT 25,
    target_duration_sec INTEGER,              -- 单集目标时长
    subtitle_lang     TEXT NOT NULL DEFAULT 'zh-CN',
    narrator_voice_id TEXT NOT NULL DEFAULT '',
    created_at        TEXT NOT NULL,
    updated_at        TEXT NOT NULL
);
```

步骤状态单独一张表，而不是 project 上的一个 `phase` 字段。
单个 `phase: str` 只能表达"走到第几步"这一条线性进度，无法表达"第 5 步已确认，
但第 3 步被改动后需要复查"这种并存状态 —— 十步各自独立确认、独立失效，
必须十行独立记录。

```sql
CREATE TABLE step_state (
    project_id   TEXT NOT NULL REFERENCES project(id) ON DELETE CASCADE,
    step         INTEGER NOT NULL,   -- 1..10
    status       TEXT NOT NULL DEFAULT 'not_started',
                 -- not_started / processing / pending_review / confirmed / needs_review
    confirmed_at TEXT,
    -- 确认时刻的上游签名快照，用于判断确认是否还有效
    confirmed_upstream_signature TEXT NOT NULL DEFAULT '',
    note         TEXT NOT NULL DEFAULT '',
    PRIMARY KEY (project_id, step)
);
```

`needs_review` 不落库为持久状态，而是查询时推导：若 `confirmed_upstream_signature`
与当前上游签名不一致，则该步骤显示为 `needs_review`。这样"改了前面 → 后面标记失效"
不需要写传播代码，改一次正文自动让十步全部亮灯。

### 4.3 小说分析（第二步）

分析结果是一份结构化文档，字段多且都是文本，用 JSON 列存整体 + 少量提取列做索引。
不为每个分析维度建表 —— 它们只被整体读写，拆表只增加 join 成本。

```sql
CREATE TABLE novel_analysis (
    id               TEXT PRIMARY KEY,
    project_id       TEXT NOT NULL REFERENCES project(id) ON DELETE CASCADE,
    version          INTEGER NOT NULL,
    -- 结构化分析结果，键固定：story_type/background/worldview/timeline/
    -- characters_major/characters_minor/relations/core_conflict/plot_beats/
    -- emotion_curve/climax/foreshadowing/chapters/episode_split/
    -- non_visual_passages/narration_candidates
    payload          TEXT NOT NULL,          -- JSON
    own_signature    TEXT NOT NULL,
    upstream_signature TEXT NOT NULL,        -- = project.source_signature
    is_current       INTEGER NOT NULL DEFAULT 0,
    generated_by     TEXT NOT NULL DEFAULT '',   -- provider:model
    created_at       TEXT NOT NULL
);
CREATE UNIQUE INDEX ux_analysis_current ON novel_analysis(project_id)
    WHERE is_current = 1;
```

`is_current` 的部分唯一索引保证一个项目同时只有一个当前版本，切换版本是两行 UPDATE，
不需要应用层保证互斥。后面所有版本化表都用同一套模式，不再重复说明。

### 4.4 剧本（第三步）

剧集 → 场次两层实体表，场次内容用 JSON。场次是用户修改的最小单位，也是失效传播的最小单位 ——
改一场只让该场次下的分镜失效，不影响整集。

```sql
CREATE TABLE screenplay (
    id         TEXT PRIMARY KEY,
    project_id TEXT NOT NULL REFERENCES project(id) ON DELETE CASCADE,
    version    INTEGER NOT NULL,
    own_signature      TEXT NOT NULL,
    upstream_signature TEXT NOT NULL,   -- = novel_analysis.own_signature
    is_current INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL
);

CREATE TABLE episode (
    id            TEXT PRIMARY KEY,
    screenplay_id TEXT NOT NULL REFERENCES screenplay(id) ON DELETE CASCADE,
    episode_no    INTEGER NOT NULL,
    title         TEXT NOT NULL DEFAULT '',
    est_duration_sec REAL NOT NULL DEFAULT 0,
    -- 节奏账本（来自 dongtai-man-rhythm）：时间轴/核心爽点/小爽点/强动态预算
    rhythm_plan   TEXT NOT NULL DEFAULT '{}',   -- JSON
    UNIQUE (screenplay_id, episode_no)
);

CREATE TABLE scene_take (              -- "场次"，避免与场景资产 scene 混名
    id            TEXT PRIMARY KEY,
    episode_id    TEXT NOT NULL REFERENCES episode(id) ON DELETE CASCADE,
    take_no       INTEGER NOT NULL,
    scene_slug    TEXT NOT NULL DEFAULT '',   -- 场景头：【内景-地点-时间（光线）】
    -- 出场人物、剧情、动作、对白、旁白、情绪、转场
    content       TEXT NOT NULL,              -- JSON
    est_duration_sec REAL NOT NULL DEFAULT 0,
    own_signature TEXT NOT NULL,              -- 分镜失效判断的上游锚点
    UNIQUE (episode_id, take_no)
);
```

`episode.rhythm_plan` 与 `dongtai-man-rhythm` 的输出结构对齐（时段/节奏/内容/动态等级/
爽点类型），第六步拆分镜时读它决定镜头密度和强动态位置，不是装饰字段。

### 4.5 资产：角色/场景/物品（第四、五步）

**关键设计决定：分镜引用资产用 `asset_id` 外键，不用名字字符串。**

按名字字符串匹配的方案（`shot.scene_name` 与 `scene.name` 相等即绑定）看起来更直观，
但有个致命问题：名字对不上时**不会报错**，只是静默不挂参考图。改一次场景名、剧本里
写成简称、多一个空格，绑定就断了，而链路照常跑完 —— 出图后才发现角色长得不对。
外键约束把这类错误变成插入时立刻失败，是**用类型系统换取静默质量损失的消失**。

名字仍然保留在 `asset.name`，但只用于显示和提示词文本，不参与任何绑定判定。

三类资产共用一张表，靠 `asset_type` 区分，避免三套几乎相同的表和三套几乎相同的接口：

```sql
CREATE TABLE asset (
    id          TEXT PRIMARY KEY,
    project_id  TEXT NOT NULL REFERENCES project(id) ON DELETE CASCADE,
    asset_type  TEXT NOT NULL CHECK (asset_type IN ('character','scene','prop')),
    name        TEXT NOT NULL,
    -- 同一地点的不同时间/状态是变体，不是新资产（林家客厅｜夜晚）
    parent_asset_id TEXT REFERENCES asset(id) ON DELETE CASCADE,
    variant_label   TEXT NOT NULL DEFAULT '',
    -- 结构化描述：角色/场景/物品各自的字段集，见下方 profile 说明
    profile     TEXT NOT NULL,              -- JSON
    -- 一致性锚点（来自 dongtai-man-character）：不可变特征 / 禁用变化 / 定妆关键词串
    consistency_anchor TEXT NOT NULL DEFAULT '{}',   -- JSON
    importance  TEXT NOT NULL DEFAULT 'normal'
                CHECK (importance IN ('core','normal','shot_only')),
    needs_reference_image INTEGER NOT NULL DEFAULT 1,
    -- 角色专属：绑定的配音音色
    voice_id    TEXT NOT NULL DEFAULT '',
    status      TEXT NOT NULL DEFAULT 'draft'
                CHECK (status IN ('draft','generating','pending_review','confirmed','locked')),
    own_signature      TEXT NOT NULL,
    upstream_signature TEXT NOT NULL,       -- = screenplay.own_signature
    created_at  TEXT NOT NULL,
    updated_at  TEXT NOT NULL,
    UNIQUE (project_id, asset_type, name, variant_label)
);
CREATE INDEX idx_asset_project_type ON asset(project_id, asset_type);
```

`importance` 三档决定第五步的质量门禁对哪些资产较真：`core`（必须有参考图，缺图时
生成关键帧直接失败）、`shot_only`（只在单镜出现，不单独出图，描述文字直接写进提示词）、
`normal`（中间态，用户可手工切换）。

不分档的后果是两头都难受：所有资产都要求出图，一部剧几百个物品全部生成一遍纯属浪费；
所有资产都不要求，主角没有定妆图也能进第六步，一致性就没了着落。

`profile` 按类型存不同字段，不拆表：

| asset_type | profile 字段 |
|---|---|
| character | `aliases[] gender age identity personality appearance hair_style hair_color body default_costume costume_variants[] acting_traits relationships[] appears_in[] needs_fixed_voice` |
| scene | `scene_type indoor_outdoor time_of_day weather architecture layout lighting color_mood furnishings[] appears_in[]` |
| prop | `description owner significance appears_in[]` |

`consistency_anchor` 是从 `dongtai-man-character` 的「一致性锚点」小节直接搬过来的，
三个键：`immutable_features[]`（发色/疤痕/眼镜/标志服装，3–6 个词）、
`forbidden_changes[]`（禁止随机换装换发型）、`keyword_string`（可直接拼进图片提示词的中文短语）。
第七步生成关键帧时，这个串必须完整出现在提示词里 —— 这是角色一致性的主要抓手。

**参考图版本表**（一个资产可以有多张图：正面/侧面/半身/全身/服装变体）：

```sql
CREATE TABLE asset_image (
    id          TEXT PRIMARY KEY,
    asset_id    TEXT NOT NULL REFERENCES asset(id) ON DELETE CASCADE,

    -- 图类：portrait_front / portrait_side / half_body / full_body / expression / costume

    negative_prompt TEXT NOT NULL DEFAULT '',
    file_path   TEXT,
    remote_url  TEXT NOT NULL DEFAULT '',     -- 图床临时链接，供视频接口引用
    remote_url_expires_at TEXT,
```

那个 partial unique index 是关键：SQLite 支持带 `WHERE` 的唯一索引，用它在数据库层保证
「每个资产每个图类只有一个当前版本」，不靠应用代码自觉。后面所有 `*_version` 表都用同一手法。

### 4.6 分镜（第六步）

分镜是全平台最重的表，字段清单对齐方案第六步的分镜要素，加上 `dongtaiman` 标准分镜块
的字段（镜头/动态效果/转场/备注）。**绑定一律用 asset_id 外键，不用名字字符串。**

```sql
CREATE TABLE shot (
    id            TEXT PRIMARY KEY,
    project_id    TEXT NOT NULL REFERENCES project(id) ON DELETE CASCADE,
    scene_take_id TEXT NOT NULL REFERENCES scene_take(id) ON DELETE CASCADE,
    shot_no       INTEGER NOT NULL,        -- 全项目连续编号，展示用
    shot_order    INTEGER NOT NULL,        -- 场次内排序，拆分/合并后重排
    -- 镜头语言
    shot_type     TEXT NOT NULL DEFAULT '',   -- 远景/全景/中景/近景/特写
    camera_angle  TEXT NOT NULL DEFAULT '',   -- 平视/俯视/仰视/过肩
    camera_move   TEXT NOT NULL DEFAULT '',   -- 推/拉/摇/移/跟/环绕/升降/固定
    shot_structure TEXT NOT NULL DEFAULT 'phased_single_take'
                   CHECK (shot_structure IN ('phased_single_take','dense_multishot')),
    -- 绑定（asset_id 外键，不是名字）
    scene_asset_id TEXT REFERENCES asset(id) ON DELETE SET NULL,
    -- 内容
    action        TEXT NOT NULL DEFAULT '',
    frame_desc    TEXT NOT NULL DEFAULT '',   -- 画面描述
    emotion       TEXT NOT NULL DEFAULT '',
    dynamic_level TEXT NOT NULL DEFAULT 'micro'
                  CHECK (dynamic_level IN ('micro','medium','strong')),
                  -- 提示词编译器映射：micro→动・基础，medium→动・中度，strong→动・特效
    transition_type TEXT NOT NULL DEFAULT ''
                    CHECK (transition_type IN ('','切','淡入','淡出','虚入','虚出','闪白','光斑转场')),
    -- 音效设计（dongtaiman 三层）：ambient 环境音 / action_sfx 动作音效 / bgm 配乐风格+时长
    audio_design_json TEXT NOT NULL DEFAULT '{"ambient":"","action_sfx":"","bgm":""}',
    -- 连续性账本：让跨镜衔接成为显式数据，不靠相邻镜头文本猜
    start_state       TEXT NOT NULL DEFAULT '',
    completed_beat    TEXT NOT NULL DEFAULT '',
    expected_end_state TEXT NOT NULL DEFAULT '',
    open_motion       TEXT NOT NULL DEFAULT '',
    next_hook         TEXT NOT NULL DEFAULT '',
    -- 时长：Grok 图生视频接受 6–30 秒整数秒，且 API 只收纯数字（不能带引号）。
    -- 所以这里用 INTEGER 而不是 REAL —— 类型即约束，序列化时不会漏掉取整。
    planned_duration_sec INTEGER NOT NULL DEFAULT 6
                         CHECK (planned_duration_sec BETWEEN 6 AND 30),
    -- 提示词
    image_prompt   TEXT NOT NULL DEFAULT '',
    video_prompt   TEXT NOT NULL DEFAULT '',
    negative_prompt TEXT NOT NULL DEFAULT '',
    -- 签名与失效
    signature      TEXT NOT NULL,
    upstream_signature TEXT NOT NULL,   -- 生成时 scene_take.own_signature
    binding_warnings TEXT NOT NULL DEFAULT '[]',   -- JSON 数组，绑定诊断
    created_at     TEXT NOT NULL,
    updated_at     TEXT NOT NULL,
    UNIQUE (project_id, shot_no)

```

分镜与角色/物品是多对多，单独建关联表。这里是修掉参考项目「按名字精确相等匹配、
对不上就静默不挂图」那个静默质量损失的地方：

```sql
CREATE TABLE shot_character (
    shot_id     TEXT NOT NULL REFERENCES shot(id) ON DELETE CASCADE,
    asset_id    TEXT NOT NULL REFERENCES asset(id) ON DELETE RESTRICT,
    -- 本镜该角色的具体行为，对齐 character_beats：说话者演台词、听者给反应，
    -- 在场者都必须有动作，杜绝有人定格
    beat        TEXT NOT NULL DEFAULT '',
    expression  TEXT NOT NULL DEFAULT '',
    position    TEXT NOT NULL DEFAULT '',   -- 画面位置/站位
    -- 本镜穿哪套衣服：指向该角色的变体 asset 行（parent_asset_id = 本行 asset_id），
    -- NULL 表示默认服装。变体本身就是 asset 行，不另建 asset_variant 表
    variant_asset_id TEXT REFERENCES asset(id) ON DELETE SET NULL,
    is_speaker  INTEGER NOT NULL DEFAULT 0,
    PRIMARY KEY (shot_id, asset_id)
);

CREATE TABLE shot_prop (
    shot_id     TEXT NOT NULL REFERENCES shot(id) ON DELETE CASCADE,
    asset_id    TEXT NOT NULL REFERENCES asset(id) ON DELETE RESTRICT,
    usage       TEXT NOT NULL DEFAULT '',   -- 本镜怎么用（握持/摆放/使用中）
    PRIMARY KEY (shot_id, asset_id)
);
```

`ON DELETE RESTRICT` 是刻意的：只要某个角色还被任何分镜引用，就不允许在第四步删掉它。
删除请求返回 409 并列出占用的分镜号，而不是级联删掉分镜。

对白按行存，不存整段字符串。这是参考项目 `dialogue_lines` 的设计，字幕、TTS、
视频表演提示词必须消费同一个文本源，否则三者会漂移：

```sql
CREATE TABLE shot_dialogue (
    id           TEXT PRIMARY KEY,
    shot_id      TEXT NOT NULL REFERENCES shot(id) ON DELETE CASCADE,
    line_order   INTEGER NOT NULL,
    -- dialogue（角色对白）/ narration（旁白）/ inner_monologue（内心独白）
    line_type    TEXT NOT NULL,
    -- 对白时指向角色 asset；旁白为 NULL
    speaker_asset_id TEXT REFERENCES asset(id) ON DELETE SET NULL,
    text         TEXT NOT NULL,
    emotion      TEXT NOT NULL DEFAULT '',
    -- 口型分级：micro（单字语气词）/ medium（≤5字）/ large（>5字）
    mouth_level  TEXT NOT NULL DEFAULT 'medium',
    -- 台词字数：DDL 不加长度限制。
    -- LLM 生成 prompt 里约束"单句不超过 10 字"（dongtai-man-writing 规范）；
    -- dongtaiman 标准块里写的是"每句不超过 20 字"，两者不同，以 10 字为提示词约束。
    -- 用户手写时给警告（>10字 提示，>20字 阻断）而不是直接 DDL 报错。
    UNIQUE (shot_id, line_order)
);
```

### 4.7 分镜媒体产物（第七、八步）

关键帧、视频、配音三类产物结构高度相似（都是「一个分镜 → 多个候选版本 → 选一个」），
但字段差异大到合并会长出一堆互不相关的空列。按类型分表，共用同一套版本约定：

```sql
CREATE TABLE keyframe_version (
    id            TEXT PRIMARY KEY,
    shot_id       TEXT NOT NULL REFERENCES shot(id) ON DELETE CASCADE,
    version_no    INTEGER NOT NULL,
    is_current    INTEGER NOT NULL DEFAULT 0,
    locked        INTEGER NOT NULL DEFAULT 0,

    file_path     TEXT,                      -- 相对 media_root
    remote_url    TEXT,                      -- 图床临时直链（送给视频 API 用）
    remote_expires_at TEXT,                  -- 直链过期时间，过期需重新上传

    -- 实际送进图像模型的完整提示词，用于页面回显和复现
    render_prompt TEXT NOT NULL DEFAULT '',
    negative_prompt TEXT NOT NULL DEFAULT '',
    -- 本次生成挂了哪些参考图，按 @image1/@image2 顺序存 asset_id，
    -- 顺序即职责契约，不能乱
    reference_ids TEXT NOT NULL DEFAULT '[]',

    upstream_signature TEXT NOT NULL,        -- 见 §5 失效判定
    prompt_signature   TEXT NOT NULL,
    source        TEXT NOT NULL DEFAULT 'generated',  -- generated / uploaded
    provider      TEXT NOT NULL DEFAULT '',
    model         TEXT NOT NULL DEFAULT '',
    error         TEXT NOT NULL DEFAULT '',
    created_at    TEXT NOT NULL,
    UNIQUE (shot_id, version_no)
);
CREATE UNIQUE INDEX ux_keyframe_current ON keyframe_version(shot_id)
    WHERE is_current = 1;
```

`reference_ids` 存的是有序 asset_id 列表而不是名字，配合 §4.5 的外键，
「参考图没挂上」这件事从静默失败变成外键错误。

`remote_url` / `remote_expires_at` 是 Grok 接口的硬需求：`image_urls` 只收**公网 URL**，
本地文件路径传不进去。所以每张要参与视频生成的关键帧必须先上传到图床拿到直链。
Grok 任务返回体里的 `expires_at` 是 **unix 时间戳**（如 `1763174708`），
落库时转 ISO 字符串存 `remote_expires_at`。提交视频任务前必须检查是否已过期 ——
关键帧生成和视频生成之间可能隔了很久（用户要逐镜确认），直链大概率已失效，
过期就重新上传换新直链，不能直接提交。

```sql
CREATE TABLE clip_version (
    id            TEXT PRIMARY KEY,
    shot_id       TEXT NOT NULL REFERENCES shot(id) ON DELETE CASCADE,
    version_no    INTEGER NOT NULL,
    is_current    INTEGER NOT NULL DEFAULT 0,
    locked        INTEGER NOT NULL DEFAULT 0,

    file_path     TEXT,
    -- 实测时长（ffprobe 读出来的，不是预估）。这是第九步配音的硬上限
    actual_duration_sec REAL,

    -- 生成时用的首帧（关键帧版本 id），失效判定要跟着它走
    keyframe_version_id TEXT REFERENCES keyframe_version(id),
    render_prompt TEXT NOT NULL DEFAULT '',
    -- 拆分存储：确定性拼装的原稿 + LLM 精简后的执行稿，便于对照排查
    prompt_original TEXT NOT NULL DEFAULT '',
    prompt_source TEXT NOT NULL DEFAULT '',   -- deterministic / llm_refined
    motion_level  TEXT NOT NULL DEFAULT '',   -- 微 / 中 / 强（见 §7.2）
    camera_move   TEXT NOT NULL DEFAULT '',

    upstream_signature TEXT NOT NULL,
    prompt_signature   TEXT NOT NULL,
    source        TEXT NOT NULL DEFAULT 'generated',
    provider      TEXT NOT NULL DEFAULT '',
    model         TEXT NOT NULL DEFAULT '',
    provider_task_id TEXT NOT NULL DEFAULT '', -- 断线重连靠它，不重复付费
    error         TEXT NOT NULL DEFAULT '',
    created_at    TEXT NOT NULL,
    UNIQUE (shot_id, version_no)
);
CREATE UNIQUE INDEX ux_clip_current ON clip_version(shot_id) WHERE is_current = 1;
```

`actual_duration_sec` 必须来自 ffprobe 实测。视频 API 给的时长和实际产出经常差
0.2–0.5 秒，而第九步的配音时长校验以这个值为准 —— 用预估值会导致校验通过但成片音画不齐。

`provider_task_id` 是从参考项目照搬的：视频生成是长任务且按次计费，进程重启后
必须能用它继续轮询原任务，不能重新提交。

### 4.8 配音、字幕（第九步，两张独立表）

方案文档要求两者同页但可分别重做，所以拆两张表、各自独立版本与确认状态。
V1 取消口型同步后处理（原因见 §7.7），口型只作为 `shot.mouth_level`
脚本标注写进视频提示词，不产生独立产物，因此没有对应的版本表。

```sql
CREATE TABLE audio_version (
    id            TEXT PRIMARY KEY,
    shot_id       TEXT NOT NULL REFERENCES shot(id) ON DELETE CASCADE,
    version_no    INTEGER NOT NULL,
    is_current    INTEGER NOT NULL DEFAULT 0,
    locked        INTEGER NOT NULL DEFAULT 0,

    file_path     TEXT,
    actual_duration_sec REAL,

    -- 时长合规（硬约束，见 §7.1）
    duration_status TEXT NOT NULL DEFAULT 'pending',
        -- pending 待校验 / ok 合规 / over 超长
    clip_duration_sec REAL,        -- 校验时对照的视频时长（快照，便于复盘）
    fit_strategy  TEXT NOT NULL DEFAULT '',
        -- '' 未处理 / atempo 变速 / trim_text 精简对白 / respeak 调语速重生成
    atempo_ratio  REAL,            -- 变速比，上限 1.15

    -- 分段与时间戳：一个镜头可能有多个说话人 + 旁白
    segments_json TEXT NOT NULL DEFAULT '[]',
        -- [{line_id, speaker, voice_id, text, start_sec, end_sec, emotion, rate}]
    word_timestamps_json TEXT NOT NULL DEFAULT '[]',

    upstream_signature TEXT NOT NULL,
    prompt_signature   TEXT NOT NULL,  -- 按 (文本, voice_id) 有序列表签名
    provider      TEXT NOT NULL DEFAULT '',
    error         TEXT NOT NULL DEFAULT '',
    created_at    TEXT NOT NULL,
    UNIQUE (shot_id, version_no)
);
CREATE UNIQUE INDEX ux_audio_current ON audio_version(shot_id) WHERE is_current = 1;
```

`prompt_signature` 按 `(文本, voice_id)` 的**有序列表**签名 —— 参考项目
`audio_segments_signature()` 的做法。只签文本会导致换音色后命中旧缓存，是个实际踩过的坑。

```sql
CREATE TABLE subtitle_version (
    id            TEXT PRIMARY KEY,
    shot_id       TEXT NOT NULL REFERENCES shot(id) ON DELETE CASCADE,
    version_no    INTEGER NOT NULL,
    is_current    INTEGER NOT NULL DEFAULT 0,
    locked        INTEGER NOT NULL DEFAULT 0,

    -- 字幕文本来自剧本，不做 ASR 回识别（方案 §9.3）
    cues_json     TEXT NOT NULL DEFAULT '[]',
        -- [{index, start_sec, end_sec, text, style}] style: dialogue / narration
    timing_source TEXT NOT NULL DEFAULT '',
        -- word_ts / sentence_ts / forced_align / asr —— 按方案的优先级顺序降级
    overlap_warnings_json TEXT NOT NULL DEFAULT '[]',

    audio_version_id TEXT REFERENCES audio_version(id),  -- 时间轴取自哪版配音
    upstream_signature TEXT NOT NULL,
    error         TEXT NOT NULL DEFAULT '',
    created_at    TEXT NOT NULL,
    UNIQUE (shot_id, version_no)
);
CREATE UNIQUE INDEX ux_subtitle_current ON subtitle_version(shot_id) WHERE is_current = 1;
```

**字幕格式决策：SRT + 合成时按 `style` 渲染，不用 ASS/SSA。**

`dongtaiman` 要求对话字幕白色 + 黑描边，旁白字幕灰色 + 无描边，位置画面下沿 1/5。
SRT 不支持样式和位置，但样式信息已在 `cues_json` 的 `style` 字段里（`dialogue` /
`narration`）。合成阶段 FFmpeg `drawtext` 根据 `style` 分别渲染颜色，SRT 文件只存
时间轴 + 文本（播放器挂载用），成片字幕效果符合 `dongtaiman` 规范。不换 ASS/SSA
格式，减少合成管线复杂度。 V1 不做口型同步后处理（见 §7.7），口型只是
`shot.mouth_level` 上的作画提示，写进视频提示词交给视频模型渲染。少这张表的连带简化：视频链保持
`clip_version` 单一环节（不存在"原视频 → 口型视频"两个交付候选），manifest 和 QC
不需要判断该用哪一版，第八步确认过的视频就是最终进成片的那一版。

### 4.9 成片与质检

```sql
CREATE TABLE render_version (
    id            TEXT PRIMARY KEY,
    project_id    TEXT NOT NULL REFERENCES project(id) ON DELETE CASCADE,
    episode_id    TEXT REFERENCES episode(id),   -- NULL = 全剧集合并导出
    version_no    INTEGER NOT NULL,
    is_current    INTEGER NOT NULL DEFAULT 0,

    file_path     TEXT,             -- final/ep01_v1.mp4
    srt_path      TEXT,             -- 同时导出的独立 SRT
    duration_sec  REAL NOT NULL DEFAULT 0,
    width         INTEGER NOT NULL DEFAULT 0,
    height        INTEGER NOT NULL DEFAULT 0,
    fps           REAL NOT NULL DEFAULT 0,

    -- 合成参数（背景音乐、音量、片头片尾）
    compose_config_json TEXT NOT NULL DEFAULT '{}',

    -- 交付质检：passed=0 时项目不得显示"已完成"
    qc_passed     INTEGER NOT NULL DEFAULT 0,
    qc_result_json TEXT NOT NULL DEFAULT '{}',
        -- {checks:{}, errors:[], actual_duration_sec, expected_duration_sec, ...}

    upstream_signature TEXT NOT NULL,
    error         TEXT NOT NULL DEFAULT '',
    created_at    TEXT NOT NULL,
    UNIQUE (project_id, episode_id, version_no)
);
```

`qc_result_json` 的结构固定为 `passed` / `checks` / `errors` / 实际与预期时长 / 分辨率 /
帧率 / 镜头数。检查项逐条落成 `checks` 里的布尔值而不是一个总的成败标志，
这样前端交付页能显示"哪一项没过"，而不是只显示"质检失败"。

**关键取舍：交付完成以 ffprobe 质检为准，不以"接口返回 200"或"文件存在"为准。**
合成命令退出码为 0 只说明 FFmpeg 没崩，不说明成片能播 —— 音轨缺失、时长对不上、
分辨率被某一段素材拖偏，这些都能安静地产出一个"看起来正常"的文件。
这也是本方案 §10「合成前检查」的落点。

## 五、版本管理与失效传播

这一节是整个设计的核心机制。方案文档第六章第 1、2、3 节（确认锁定、版本管理、单项
重新生成）的正确性全部依赖它，实现时最容易出错的地方也集中在这里。

### 5.1 版本表统一模式

所有可生成产物遵循同一套约定，不为每类产物单独设计一套机制：

```
每次生成插入一行，永不覆盖、永不删除
is_current = 1 标记当前生效版本（partial unique index 保证唯一）
locked = 1 表示用户已确认锁定
upstream_signature 记录生成时的上游签名（失效判定唯一依据）
```

具体到本项目，版本表有 8 张：

| 版本表 | 稳定身份 | 一个版本代表 | 唯一约束 |
|--------|---------|--------------|---------|
| `novel_analysis` | 项目 | 一次完整小说分析 | `(project_id)` where current |
| `screenplay` | 项目 | 一次完整剧本改编 | `(project_id)` where current |
| `asset_image` | 素材 + 图类 | 一张参考图 | `(asset_id, image_kind)` where current |
| `keyframe_version` | 分镜 | 一张关键帧 | `(shot_id)` where current |
| `clip_version` | 分镜 | 一段视频 | `(shot_id)` where current |
| `audio_version` | 分镜 | 一份配音 | `(shot_id)` where current |
| `subtitle_version` | 分镜 | 一份字幕时间轴 | `(shot_id)` where current |
| `render_version` | 剧集 | 一次合成输出 | `(project_id, episode_id)` |

两点与「主表 + 版本表」的教科书写法不同，都是刻意的：

**一、项目级产物没有独立主表。** `novel_analysis` / `screenplay` 每行就是一个版本，
稳定身份由 `project_id` 承担 —— 再建一张只有"指向当前版本"一个字段的主表是纯冗余。

**二、四类分镜媒体各自建表，不合并成一张 `shot_media` + `media_kind`。** 合并看起来
能省三份相似 DDL，但四类产物的差异字段比共同字段多：关键帧要 `remote_url` /
`remote_expires_at` / `reference_ids`，视频要 `actual_duration_sec` /
`provider_task_id` / `keyframe_version_id`，配音要 `duration_status` / `fit_strategy` /
`atempo_ratio` / `segments_json`，字幕要 `cues_json` / `timing_source`。合并后得到
一张 30+ 列的表，每行有一半列是 NULL，且无法用 CHECK 约束表达"视频行必须有时长"
这类规则。宽表加空列的代价比重复 DDL 更高。

### 5.2 签名派生链

签名是失效判定的唯一依据。**不做事件式传播，不写"标记下游 stale"的递归函数。**
每个产物记录它当时依赖的上游签名，读取时现算当前上游签名并比对：

```
source_signature      = sha256(小说正文)
                              ↓
analysis_signature    = sha256(确认版分析内容)
                              ↓
screenplay_signature  = sha256(确认版剧本内容)
                       ↓                    ↓
asset_signature        storyboard_signature = sha256(全部分镜语义)
（单素材：素材描述 + 一致性锚点 + 画风）      ↓
                       ↓            shot_signature = sha256(单镜语义字段)
                       └──────┬─────────────┘
                              ↓
              keyframe_signature = sha256(shot_sig + 引用素材签名集 + 提示词 + 画风)
                              ↓
              video_signature    = sha256(keyframe_sig + 视频提示词 + 时长)
                              ↓
              audio_signature    = sha256(对白文本 + voice_id + 语速音调)
                              ↓
              subtitle_signature = sha256(audio_sig + 字幕文本)
                              ↓
              final_signature    = sha256(全部已确认 shot 产物签名)
```

`shot_signature` 只覆盖**语义字段**（场景、角色、物品、景别、运镜、动作、对白、时
长、情绪、连续性），**不含任何媒体路径或生成结果**。这条约束不能破：如果签名里混进
了生成结果，那么生成一张关键帧就会让 `shot_signature` 变化，进而让刚生成的这张图自己
失效 —— 变成永远无法达到"已确认且不失效"的死循环。

判断某字段该不该进签名的标准：**它变了，下游产物是否真的需要重做**。改 `action` 要重做
关键帧，进签名；改 `image_path` 只是换了个存储位置，不进。

### 5.3 stale 是算出来的，不是存出来的

方案文档里定义了 `stale` / `stale_reason` / `stale_source` 三个字段。实现上它们
**不是权威状态，而是计算结果的缓存**：

```python
def compute_stale(version_row, current_upstream_sig: str) -> tuple[bool, str]:
    """失效判定：上游签名对不上就是失效。单一判据，无递归。"""
    if version_row.upstream_signature != current_upstream_sig:
        return True, f"上游已变更（{version_row.upstream_kind}）"
    return False, ""
```

为什么不用事件传播：改一处剧本要递归标记该场次下所有分镜、每个分镜的关键帧、视
频、配音、字幕 —— 一次修改动辄上百行 UPDATE，任何一条漏掉就是静默错误，而且这类
错误只在最终合成时才暴露。签名比对是**幂等**的，读多少次结果都一样，漏不掉。

写库时机：产物列表 API 每次查询时现算并回填 `stale` 列，供 UI 直接渲染。回填失败不
影响正确性，因为下一次查询还会再算。

### 5.4 步骤状态由 stale 推导

方案文档里左侧导航的五种状态，不单独维护，从数据推导：

| 导航状态 | 推导规则 |
|----------|----------|
| 未开始 | 该步骤无任何版本行 |
| 处理中 | 该步骤有 `queued`/`running`/`waiting_provider` 的 job |
| 待确认 | 有版本行，但 `confirmed_version_id IS NULL` |
| 已确认 | `confirmed_version_id` 非空，且该版本 `stale = false` |
| 需要修改 | `confirmed_version_id` 非空，但该版本或其下游存在 `stale = true` |

单独维护一份步骤状态，就得在每次生成、确认、修改、失效时同步更新，这是第二份真相
来源。一个手写的 `phase` 字段和实际产物状态迟早会不一致 —— 漏更新一处，它就从依据
退化成参考，而排查"为什么显示已确认但实际缺图"要比直接从产物推导贵得多。

### 5.5 失效不删除产物

方案文档明确"不能直接删除后续内容"，实现上对应两条硬规则：

1. **失效产物保留完整可播放**。UI 打标但不禁用预览。用户可能只是改了一个错别字，
   下游其实还能用。
2. **重生成先写 temp 再原子替换**。新产物落 `temp/`，校验通过后 `os.replace()` 覆盖
   正式路径。生成失败时旧产物完好无损。文本（JSON 快照）和二进制媒体走同一套
   写入函数，避免两条路径两种可靠性。

### 5.6 防止旧媒体复活

最容易踩的一类 bug：媒体只按 `shot_001.png` 这样的文件名回显。正文改了以后分镜重新
生成，1 号镜头的内容已经完全不同，但文件名还是 `shot_001.png` —— 新的 1 号镜头就挂上
了旧的 1 号镜头的图。这类错误不报任何异常，页面看起来一切正常，直到成片里出现对不上
剧情的画面。

本项目的规则：**回显必须校验签名，文件存在不等于可用**。

```python
def resolve_media(shot, media_kind: str) -> ShotMediaVersion | None:
    """只有签名匹配当前镜头语义的产物才允许回显。"""
    version = get_current_version(shot.id, media_kind)
    if version is None:
        return None
    if version.upstream_signature != current_upstream_signature(shot, media_kind):
        return None      # 有文件，但不属于当前镜头，不挂回
    return version
```

## 六、任务中心与后台执行

方案文档第六章第 5 节要求统一任务中心。这一章的设计围绕两个必须回答的问题展开：
**服务重启后已提交的付费任务怎么接回来**，以及**批量任务中途失败后已完成的部分怎么保住**。

### 6.1 为什么长任务不能绑在 HTTP 请求上

生成一集的关键帧要几分钟，视频要十几分钟。如果做成同步请求：

- 浏览器刷新 → 进度全丢，无法知道服务端还在不在跑
- 连接超时 → 已经付费调用的结果拿不回来
- 服务重启 → 正在等待的 provider 任务彻底失联，只能重新付费

所以所有 AI 调用一律走后台任务：接口立刻返回 `202 Accepted` + `job_id`，前端轮询。

### 6.2 job 表

```sql
CREATE TABLE job (
    id                TEXT PRIMARY KEY,
    project_id        TEXT NOT NULL REFERENCES project(id),
    job_type          TEXT NOT NULL,
    -- 任务目标（按 job_type 取用其中之一）
```

### 6.3 job_type 清单

| job_type | 目标字段 | 说明 |
|----------|----------|------|
| `analyze_novel` | target_step | 第 2 步小说分析 |
| `adapt_screenplay` | target_step | 第 3 步剧本改编 |
| `extract_assets` | target_step | 第 4 步素材提取 |
| `gen_asset_image` | target_asset_id | 单个角色/场景/物品参考图 |
| `extract_shots` | target_step | 第 6 步分镜提取 |
| `gen_keyframe` | target_shot_id | 单镜关键帧 |
| `gen_video` | target_shot_id | 单镜视频 |
| `gen_audio` | target_shot_id | 单镜配音 |
| `gen_subtitle` | target_shot_id | 单镜字幕时间轴 |
| `compose` | target_step | 第 10 步合成 |
| `qc` | target_step | 成片质检 |
| `batch` | target_step | 批量任务父节点，只做编排不干活 |

### 6.4 状态机

```
queued ──► running ──┬─► completed
                     ├─► waiting_provider ──► running ──► completed
                     ├─► failed
                     ├─► qc_failed
                     └─► interrupted   （服务重启且无安全 checkpoint）
```

- `waiting_provider` 是关键状态：视频生成提交后先把 `provider_task_id`
  落库**再**进入轮询。服务重启后拿着 task_id 继续查，不重新提交 —— 视频生成按次计费，
  重复提交等于白花一次钱，而且新任务的结果可能和用户已经看到的预览不一致。
- `interrupted` 而不是直接 `failed`：区分"没跑完"和"跑失败了"，前者产物仍可用。
- `qc_failed` 单独一档：合成接口成功 ≠ 成片可交付，见 6.7。

### 6.5 并发与互斥

互斥粒度不能一刀切。项目级单飞（同项目只允许一个任务）会让"改一个角色的参考图"
挡住"另一个角色正在生成"，自用平台里这种排队很烦；完全不互斥则会出现两个任务
同时写同一个产物。规则按冲突域划分：

| 冲突判定 | 规则 |
|----------|------|
| 同一 `target_shot_id` 的同 `job_type` | 拒绝，返回 409 |
| 同一 `target_asset_id` 的 `gen_asset_image` | 拒绝，返回 409 |
| 同一 `target_step` 的步骤级任务 | 拒绝，返回 409 |
| 不同分镜的同类任务 | 允许并发，受全局 worker 数限制 |
| 步骤级任务 与 该步骤下的单项任务 | 拒绝，避免整体重生成和单项重生成互相覆盖 |

批量生成不是一个大任务，而是**一个 `batch` 父任务 + N 个子任务**。这样：

- 单镜失败只影响该镜，其余继续（方案文档第八步的硬要求）
- 前端能显示 "37/52 完成，3 失败"
- 重试只重试失败的子任务，不重跑已成功的

worker 数按 provider 类型分池，避免图片任务把视频任务的槽位占满：

```python
WORKER_POOLS = {
    "text":  2,   # LLM 分析/改编/分镜
    "image": 4,   # 关键帧、参考图
    "video": 2,   # 视频生成（贵且慢，限流）
    "audio": 4,   # TTS
    "local": 2,   # FFmpeg 合成、质检
}
```

### 6.6 checkpoint 与续跑

`job.checkpoint` 存 JSON，语义按 job_type 区分：

| job_type | checkpoint 内容 | 续跑行为 |
|----------|-----------------|----------|
| `extract_shots` | `{"done_scene_ids": [...], "partial_shots": [...]}` | 从未完成场次继续，已生成分镜不重跑 |
| `analyze_novel` | `{"done_chunk_index": 3}` | 长文分块分析，从第 4 块继续 |
| `gen_video` | `{"provider_task_id": "...", "submitted_at": "..."}` | 拿 task_id 继续轮询，**不重新提交** |
| `compose` | `{"concat_list_path": "...", "stage": "audio_mix"}` | 从已完成的中间文件继续 |
| 其他单项任务 | `{}` | 直接重跑，成本低无需 checkpoint |

服务启动时扫描所有非终态任务（`JobRunner.recover()` 的等价逻辑）：

```
status == "waiting_provider" → 重新提交轮询（用已存的 provider_task_id）
status in ("queued",)        → 重新入队
status == "running" 且有 checkpoint → 重新入队，从 checkpoint 续跑
status == "running" 且无 checkpoint → 标记 interrupted，产物保留，等用户手动重试
```

最后一条是这套恢复逻辑里最容易写错的地方：`running` 状态只说明进程死掉时任务在跑，
不说明跑到哪了。没有 checkpoint 就无脑重跑，等于把已经付过费的调用再付一遍。
宁可标 `interrupted` 让用户点一下重试，也不要静默烧钱。

### 6.7 交付质检（QC）

第十步合成完成后必须跑质检，**接口成功不等于交付完成**。检查项分两级
（对应方案文档第十步的阻断/警告分级）：

**阻断项（P0，不允许忽略）**

| 检查 | 判定 |
|------|------|
| 成片文件存在且非空 | `stat().st_size > 0` |
| 成片可解码 | `ffprobe` 返回 0 |
| 含视频流 + 音频流 | streams 里各有一条 |
| 分辨率 = 1920×1080 | 精确相等 |
| 帧率符合配置 | 误差 ≤ 0.1 |
| 画幅比例 = 16:9 | 误差 ≤ 0.01 |
| 实际时长 ≈ 分镜时长总和 | 误差 ≤ max(1.0s, 总时长×5%) |
| 所有分镜视频均进入成片 | 逐镜 `video_path` 可解码 |
| 需配音分镜均有可解码音频 | 按 `audio_type != 'none'` 检查 |
| 无 `duration_status = 'over'` 的配音 | 本平台新增，见 5.4 |

**警告项（P1，可确认忽略）**

字幕行数偏多、SRT 时间轴有重叠、转场时长偏短、背景音乐缺失。

QC 结果整体落 `project.qc_result` JSON，失败时 job 状态为 `qc_failed`，
项目**不能**标记 `completed`。前端交付页展示逐项结果，不只显示"成功/失败"。

## 七、领域约束（从 skill 移植）

这一章是本设计与通用视频工具的区别所在。以下规则不是"AI 自由发挥"，
而是硬编码进 prompt 模板与校验器的**可判定约束**，全部来自本机 5 个动态漫 skill。

### 7.1 动态等级预算（来自 dongtai-man-writing / rhythm）

三级动态，写入 `shot.dynamic_level`：

| 等级 | 枚举值（DB） | `dongtaiman` 分镜块标注 | 含义 | 预算 |
|------|------------|------------------------|------|------|
| 微动态 | `micro` | `【动・基础】` | 头发轻飘、眼皮颤动、镜头缓推 | 不限 |
| 中动态 | `medium` | `【动・中度】` | 肢体位移、物体小幅运动、镜头切换 | 不限 |
| 强动态 | `strong` | `【动・特效】` | 打斗、爆炸、粒子效果、闪白震动 | **单集 ≤ 3** |

**命名说明：** DB 用 `micro/medium/strong`（`dongtai-man-writing` 的叫法），
`dongtaiman` 标准分镜块和 `seedance-manual` 时间轴提示词里用 `基础/中度/特效`。
提示词编译器在生成分镜文本和视频提示词时必须做这个映射，不能直接把 `strong` 写进去。

`strong` 的预算是**校验器强制**的，不是建议：分镜提取完成后统计每集
`dynamic_level = 'strong'` 的分镜数，超过 3 个则在确认时阻断，
要求用户降级或合并。原因是强动态直接对应视频 API 的高失败率和高成本。

动态分层写入 `shot.image_prompt`：前景中/强、中景微、背景静态虚化。

### 7.2 节奏时间轴（来自 dongtai-man-rhythm）

剧本改编阶段（第三步）产出 `episode.rhythm_plan` JSON，结构：

```json
{
  "target_duration_sec": 240,
  "segments": [
    {"range_sec": [0, 30],    "pace": "slow", "purpose": "铺垫",     "dynamic": "micro"},
    {"range_sec": [30, 90],   "pace": "slow", "purpose": "压抑",     "dynamic": "medium"},
    {"range_sec": [90, 120],  "pace": "fast", "purpose": "核心爽点", "dynamic": "strong"},
    {"range_sec": [120, 180], "pace": "mid",  "purpose": "小爽点",   "dynamic": "medium"}
  ],
  "core_climax": {"type": "反转打脸", "setup": "...", "burst": "...", "visual": "..."},
  "minor_climaxes": [...]
}
```

校验规则（分镜提取后自动检查，违反则警告不阻断）：

- 同节奏连续不超过 120 秒（慢 ≤ 90s，快 ≤ 60s）
- 无爽点平淡期不超过 60 秒
- 每集至少 1 个核心爽点
- 每 45 秒至少 1 个小冲突

核心公式来自 skill：**节奏起伏 = 压抑铺垫（慢）→ 爆发反转（快）**，无压抑则无爽感。
剧本改编的 prompt 里显式给出这个公式和时间轴表。

### 7.3 一致性锚点（来自 dongtai-man-character）

`asset.consistency_anchor` 是角色一致性的核心字段，JSON 结构：

```json
{
  "immutable": ["黑短发", "红围巾", "左眉骨疤痕", "工装外套"],
  "forbidden_changes": ["禁止换发型", "禁止换围巾颜色"],
  "keyword_string": "黑色短发，红色围巾，左眉骨细疤，深灰工装外套"
}
```

三处强制使用：

1. **角色参考图生成**（第五步）— `keyword_string` 必须完整出现在 prompt 中
2. **关键帧生成**（第七步）— 该角色出镜时，`keyword_string` 追加进 prompt
3. **校验器** — 生成后比对 prompt 文本是否包含 `immutable` 的每一项，缺失则拒绝提交

`immutable` 控制在 3–6 个词。skill 明确要求「短发+固定发饰」优于「长发飘飘」，
因为固定特征便于动态设计与跨镜一致。

角色小传的其他字段（显性性格、隐性反差、行为触发点、核心动作习惯、微动态特征）
写入 `asset.description`，作为 `character_beats` 生成的依据 ——
skill 要求每个在场角色都有符合性格的反应，不允许有人定格。

避坑规则（写入 prompt 的负面指令）：禁止抽象描述。
"性格温柔" → "语速放缓，嘴角微扬"；"内向" → "低头，双手攥衣角（幅度 1cm）"。

### 7.4 分镜密度（来自方案第六步）

一个分镜只承载一个可观察的剧情结果。方案里的反例：

> 角色站起来，走到门口，打开门，看见敌人后震惊地后退。

必须拆成 5 个分镜。校验器的可判定实现：统计 `shot.action` 中的
动词短语数量，超过 2 个则标记 `needs_split` 警告。

`shot_structure` 两种模式，决定提示词能不能出现剪辑语言：

| 值 | 含义 | 提示词约束 |
|----|------|-----------|
| `phased_single_take` | 默认，单镜连续运动 | **禁止**出现"切近景""插入特写"等剪辑语言 |
| `dense_multishot` | 镜内确需多个构图 | 必须输出明确的 Shot 1/2/3 结构 |

两种模式的提示词语法互斥，校验器检查：`phased_single_take` 的
`video_prompt` 不得包含剪辑词表（切/剪/insert/cut to）。

**6 秒下限带来的容量约束（Grok 定档后新增）。** Grok 的 `duration` 最小 6 秒，
这与"一镜一事"的拆分标准产生了真实张力：上面那个反例拆成 5 个分镜，
最少就要 30 秒。按单集 3–5 分钟（180–300 秒）算，每集镜头数上限是：

```
max_shots = floor(target_duration_sec / 6)
→ 180 秒 → 30 个镜头
→ 300 秒 → 50 个镜头
```

**拆分标准不放松** —— 一镜一事是对的，视频模型处理复合动作的失败率很高。
要调整的是每集容量：剧情节点太密、6 秒 × 镜头数装不下时，
**拆成两集**，而不是把多个动作塞回一个镜头。

落地方式：
- 分镜提取的 prompt 里直接给出 `max_shots` 上限
- 第六步确认时校验 `SUM(planned_duration_sec) <= target_duration_sec`，
  超出则阻断并提示"合并镜头或拆集"，避免生成完关键帧才发现时长溢出

### 7.5 参考图职责契约（来自 seedance-manual 的 `@素材` 规范）

参考图的顺序和职责是同一个不可变契约，提示词里必须显式声明：

```
@image1 controls character identity only
@image2 controls environment layout only
@image3 controls prop appearance only
@image4 controls current shot keyframe only
@image5 controls opening frame continuity only
```

序号由 `keyframe_version.reference_ids`（有序 asset_id 数组）的**下标**决定，
职责由下标位置固定。数组顺序即契约，不额外存 role 字段 —— 多一个字段就多一处
可能与顺序对不上的地方。提交前校验：

- 关键身份图（character 类 slot）缺失 → **任务失败**，不静默降级
- 当前关键帧缺失（视频生成时）→ **任务失败**
- 场景图、物品图缺失 → 警告，允许继续（写入 `binding_warnings`）
- **参考图总数超过 7 张** → 提示用户并按下表丢弃到 7 张以内

**Grok 的 7 张上限收紧了槽位分配。** `seedance-manual` 按 9 张写的，Grok 只收 7 张，
`image_urls` 装不下最坏情况（3 角色 + 1 场景 + 2 道具 + 1 关键帧 = 7 张，
再加开场帧连续性参考就溢出）。溢出时不能让用户自己猜该删哪张 —— 定死丢弃优先级：

| 优先级 | 槽位 | 能否丢 | 理由 |
|--------|------|--------|------|
| 1 | 当前关键帧 | **绝不丢** | 丢了就退化成纯文生视频，构图完全失控 |
| 2 | 说话角色身份图 | **绝不丢** | 丢了角色漂移，且漂移不报错 |
| 3 | 场景图 | 可丢 | 场景信息已隐含在关键帧构图里 |
| 4 | 非说话角色身份图 | 可丢 | 配角短暂出镜时漂移的代价较小 |
| 5 | 开场帧连续性参考 | 可丢 | 硬连续性镜头之外并非必需 |
| 6 | 道具图 | **先丢** | 道具外观已在关键帧里定好，重复传收益最低 |

丢弃时写入 `binding_warnings`，页面上要能看到"本镜丢了哪几张参考图"，
不能静默丢完就生成。

这里最需要防的是**静默降级**：参考图失效后被跳过，生成照常进行，出来的角色漂移了
但没有任何报错。V1 用 `asset_id` 外键 + 提交前存在性校验双重防护 —— 身份图缺失是
硬失败，不是警告。

### 7.6 音频单一来源

视频生成 API 的原生音频（如 Seedance `enable_sound`）必须**关闭**。
对白、旁白、内心独白的唯一声音来源是 TTS，否则成片出现双重对白。

`shot.audio_type` 四值枚举：`dialogue` / `narration` / `inner_monologue` / `none`。
归一化处理别名（对白/旁白/voiceover/内心独白 → 标准值），
并做一致性回退：声明 `dialogue` 但无对白文本时降级为 `none`。

字幕、TTS、视频表演提示词消费**同一个** `shot_dialogue` 行，
不允许字幕用一份文本、配音用另一份。

### 7.7 口型是提示词标注，不是后期同步

V1 不实现口型同步后处理，`shot.mouth_level` 只作为提示词字段参与视频生成。

分级规则直接沿用 `dongtai-man-writing`：

| 级别 | 判定 | 写进视频提示词的表述 |
|------|------|---------------------|
| `micro` | 单字 / 语气词（"嗯""哦"） | 嘴部轻微开合 |
| `medium` | ≤ 5 字短句 | 嘴部中等幅度开合 |
| `large` | > 5 字长句 | 嘴部明显开合，口型放大 |

不做后期同步的原因：

1. **模型不匹配** —— Wav2Lip / SadTalker / LatentSync 及商业 API 都基于真人脸训练。
   漫剧风格脸部检测失败或产生嘴部畸变，效果比不做更差。而 `seedance-manual`
   明确不支持写实真人脸素材，无法靠"换成真人脸"绕开。
2. **破坏已确认版本** —— 口型同步是后处理，输出新文件。第八步刚确认过的
   `clip_version` 会被顶替，交付的不是用户确认的那一版。这还会让 `clip` 链
   分叉成"原视频 / 口型视频"两个交付候选，manifest 和 QC 都要额外判断用哪个。
3. **可用镜头本来就少** —— 方案 §9.4 的跳过条件（超远景、背影、遮挡、
   快速动作、纯旁白）会滤掉大部分镜头，剩下的近景不足以支撑一个子系统。

后续要加的话，是独立迭代：新增 `lipsync_version` 表 + provider + 一层
manifest 选择逻辑，不影响本轮 schema。

## 八、十步流程与数据模型的对应

| 步骤 | 主要写入表 | 产出 | 确认动作 |
|------|-----------|------|---------|
| 1 创建项目 | `project` | 正文 + 项目配置 | 无（保存即可） |
| 2 小说分析 | `novel_analysis` | 分析 JSON | `step_state[2].status='confirmed'` + 签名快照 |
| 3 剧本改编 | `screenplay` / `episode` / `scene_take` | 剧集场次树 | 锁定剧本版本 |
| 4 素材提取 | `asset` | 角色/场景/物品清单 | 逐项 `confirmed`，整步锁定 |
| 5 素材生成 | `asset_image` | 参考图 | 逐项 `locked`，`core` 素材必须锁定 |
| 6 分镜提取 | `shot` / `shot_dialogue` / `shot_character` / `shot_prop` | 分镜清单 | 整步锁定 |
| 7 关键帧生成 | `keyframe_version` | 每镜一张图 | 逐镜 `locked=1` |
| 8 视频生成 | `clip_version` | 每镜一段视频 | 逐镜 `is_current` + 确认 |
| 9 配音字幕 | `audio_version` / `subtitle_version` | 音频+时间轴 | 两项分别确认 |
| 10 合成导出 | `render_version` | 成片 MP4 + SRT | QC 通过才算完成 |

### 8.1 每步的准入校验（gate）

进入下一步前，后端校验前置条件，不满足直接返回 409 并说明原因：

| 进入步骤 | 准入条件 |
|---------|---------|
| 3 剧本改编 | 步骤 2 已锁定 |
| 4 素材提取 | 步骤 3 已锁定（提取基于剧本，不是原小说） |
| 5 素材生成 | 步骤 4 已锁定 |
| 6 分镜提取 | 所有 `importance='core'` 的素材 `status='locked'` |
| 7 关键帧生成 | 步骤 6 已锁定 |
| 8 视频生成 | 该镜 `keyframe_version.locked=1`（逐镜校验，不是整步） |
| 9 配音字幕 | 该镜有 `is_current` 的 `clip_version`；有对白角色已绑定 `voice_id` |
| 10 合成导出 | 全部镜头 video/audio/subtitle 已确认，无 stale |

步骤 7→8 和 8→9 是**逐镜准入**，允许部分镜头已经进到第 9 步、
另一部分还在第 8 步重生成。这是原方案「不影响其他已完成内容」的落地方式。

### 8.2 批量操作的粒度

批量按钮生成一个 job，job 内部循环单项。单项失败不中止整个 job：
失败项写入对应版本表的 `error` 列并继续下一项，job 最终状态为
`completed`（部分失败）并在 `result` 里列出失败清单。

| 批量入口 | 粒度选项 |
|---------|---------|
| 素材生成 | 全部 / 仅角色 / 仅场景 / 仅物品 / 仅未生成 |
| 关键帧生成 | 全部 / 当前剧集 / 当前场次 / 仅未生成 / 仅失效 |
| 视频生成 | 全部 / 当前剧集 / 当前场次 / 仅未生成 / 仅失败 |
| 配音 | 全部有对白镜头 / 单个角色的全部台词 / 仅超时镜头 |
| 字幕 | 全部有配音镜头 / 仅未生成 / 仅失效 |

## 九、实施顺序

按依赖关系分 6 个阶段，每阶段可独立验证：

| 阶段 | 内容 | 验证方式 |
|------|------|---------|
| 1 | SQLite schema + Pydantic 模型 + 签名函数 + Alembic 初始迁移 | pytest：建库、CRUD、签名稳定性、stale 判定 |
| 2 | Job 表 + JobRunner + 恢复逻辑 + `/api/jobs` | pytest：状态机、重启恢复、409 冲突、断点续跑 |
| 3 | Provider 抽象层 + MOCK_MODE + 步骤 1–3（项目/分析/剧本） | pytest：mock 全链路；手工验证网页前三步 |
| 4 | 步骤 4–6（素材提取/生成/分镜）+ 参考图绑定 | pytest：绑定契约、缺图失败、批量部分失败 |
| 5 | 步骤 7–9（关键帧/视频/配音字幕）+ 配音时长约束 | pytest：配音超时三种处理；手工验证逐镜确认 |
| 6 | 步骤 10 合成 + QC + Playwright 端到端 | QC 断言 + 浏览器端到端（同步 API + Page Object） |

**MOCK_MODE 优先**：阶段 1–2 完成后就要能在 `MOCK_MODE=true` 下跑通全链路，
不依赖任何外部 API —— 图片返回占位图、视频返回静态帧循环、TTS 返回静音音频。

这条不是为了测试方便，是为了让开发节奏和 API 额度解耦。状态机、失效传播、
版本切换、批量部分失败这些逻辑要反复跑几十遍才能调对，每次都真调付费接口
既慢又贵。MOCK 产物只要格式合法（能被 ffprobe 解析、时长可控），
就足够验证除画面质量以外的全部逻辑。

## 十、测试策略

沿用工作区既有约定（pytest 风格、fixture 进 conftest.py、参数化、
命名 `test_<场景>_<预期结果>`、Playwright 同步 API + Page Object）。

### 10.1 必须覆盖的后端用例

| 主题 | 用例要点 |
|------|---------|
| 签名 | 同输入签名稳定；改任一参与字段签名变化；不参与字段（如 `image_path`）不影响签名 |
| stale 判定 | 改剧本使下游 stale；改素材 prompt 使引用它的关键帧 stale；改 `image_path` 不使任何东西 stale |
| 版本管理 | 重生成不覆盖旧版本；切换 current 版本；删除 current 版本被拒 |
| 准入校验 | 关键素材未锁定时进分镜返回 409；关键帧未锁定时该镜生视频返回 409 |
| 配音时长 | 超时触发变速；超 1.15 倍上限时拒绝并要求精简；精简后通过 |
| 绑定 | asset_id 绑定成功；素材被删除时绑定报错而非静默跳过；`binding_warnings` 非空时阻断 |
| Job | 状态机流转；重启后 `waiting_provider` 继续轮询原 task_id；`running` 无 checkpoint 标记 interrupted |
| 批量部分失败 | 5 项中 2 项失败，job 仍 completed，result 列出失败项，成功项产物保留 |
| QC | 分辨率/帧率/时长/流缺失各自触发对应错误；全通过时 passed=true |

### 10.2 端到端（Playwright，MOCK_MODE）

一条主链路走完 10 步，每步验证「生成 → 编辑 → 确认 → 下一步解锁」，
中途刷新页面验证任务状态和产物恢复。测试用新建项目，跑完清理，不动已有数据。

### 11.2 仍待确认

1. **是否要与动态漫 skill 双向互通**。schema 已经吃下了 skill 的全部字段
   （一致性锚点、动态三级、嘴部幅度、强动态预算、节奏时间轴），
   所以平台产物和 skill 产物在语义上是对齐的。缺的只是一层文本格式适配 ——
   把 `shot` 表导出成 `04_标准分镜.md` 那种块格式，或反向解析导入。
   如果你希望「用 skill 手写一集、导入平台出图出片」，或者
   「平台拆完分镜、导出给 skill 精修」，就需要这层适配。不做也不影响平台自身闭环。
